Depuración y Corrección de Expresiones

Guía práctica y metodológica para identificar, analizar, solucionar y prevenir errores comunes dentro de sus flujos automatizados.

Identificar el Tipo de Error

Antes de corregir una expresión, es fundamental catalogar el momento y la naturaleza de la falla. Los errores se dividen principalmente en dos etapas:

1. Errores de Diseño (Compilación)

Ocurren mientras editas el flujo. El diseñador detecta problemas de sintaxis impidiendo guardar el proceso.

Ejemplo: InvalidTemplate. Ocurre al escribir mal una función o faltar paréntesis.

2. Errores en Tiempo de Ejecución

El flujo se guarda correctamente, pero falla al procesar datos reales debido a nulos o incompatibilidades operativas.

Ejemplo: ExpressionEvaluationFailed. Se intenta leer un nodo JSON inexistente.

Herramientas de Depuración Integradas

Microsoft suministra múltiples utilidades nativas para inspeccionar el comportamiento de las expresiones.

Editor de Expresiones

Valida la sintaxis en tiempo real, asiste con autocompletado y resalta fallos.

Copilot / IA

Permite describir la corrección requerida en lenguaje natural y genera la sintaxis limpia.

Historial

Expone detalladamente los bloques JSON exactos de entrada y salida de cada acción.

Metodología de Análisis de Errores

Frente a un fallo crítico, siga esta secuencia estructurada paso a paso para diagnosticar la raíz del problema rápidamente:

1

Inputs/Outputs

Abra la acción e inspeccione los payloads JSON.

2

Validar Datos

Compare tipo recibido contra el esperado.

3

Detectar Nulos

Verifique si campos obligatorios llegaron vacíos.

4

Rastrear Origen

Analice si flujos previos mutaron el dato.

Defensa contra Nulos con empty()

Procesar colecciones o textos vacíos con funciones como first() causa una excepción fatal. La función empty() previene esto evaluando la existencia previa de los datos.

Sintaxis Defensiva Recomendada:

if(empty(variables('lista')), null, first(variables('lista')))

¿Por qué evita interrupciones?

Evalúa de forma booleana. Si el objeto está vacío, devuelve inmediatamente un valor controlado alternativo (como null) en lugar de intentar ejecutar la función principal en el vacío.

El Operador de Navegación Segura ?.

Si un nodo o propiedad JSON raíz no viene en la respuesta, el motor rompe el flujo. La notación segura absorbe la ausencia de campos devolviendo un estado nulo controlado.

Método de Acceso Ejemplo de Expresión Resultado si no existe
Estándar (Inseguro) triggerBody()['Contacto']['Telefono'] Fallo (Rompe el flujo)
Seguro (Recomendado) triggerBody()?['Contacto']?['Telefono'] Exitoso: Devuelve Null

Conversión Explícita de Tipos (Casting)

Power Automate rechaza realizar operaciones lógicas si los tipos no coinciden (ej. intentar validar el texto de un número "5" contra un entero 5).

Funciones Clave

• int(): Texto a números enteros.

• float(): Texto a decimales.

• string(): Convierte objetos a texto.

• parseDateTime(): Texto a Formato Fecha.

Caso Práctico

// Incorrecto (Falla si id es texto): greater(triggerBody()?['id'], 100) // Solución Correcta: greater(int(triggerBody()?['id']), 100)

Manipulación String y Sensibilidad de Texto

Las funciones de comparación de cadenas de texto como contains() o equals() son estrictamente sensibles a mayúsculas y minúsculas (Case-Sensitive).

Estandarización Preventiva

Para asegurar la coincidencia sin importar cómo escribió el usuario, convierta siempre los valores de los extremos a minúsculas usando la función toLower().

contains(toLower(triggerBody()?['correo']), 'aprobado')

Checklist de Producción Completa

Implemente esta verificación técnica e interactiva antes de pasar cualquier flujo de Power Automate a entornos de producción:

  • ¿He envuelto las llamadas dinámicas con el operador de navegación segura ??
  • ¿Usé la función empty() en arreglos opcionales para prevenir fallas fatales?
  • ¿He tipificado explícitamente mediante int() o string() los campos de comparación?
  • ¿He aplicado toLower() en condiciones para anular la sensibilidad a mayúsculas?
